## Review

This change fails the user's explicit requirement. Stripe delivers `payment_intent.succeeded` at-least-once, and the surrounding context confirms redelivery happens when the 200 acknowledgement is lost to a timeout — yet the handler performs a blind `UPDATE ... SET balance = balance + $2` on every arrival with no record of already-processed events. There is no `processed_events` table, no `Idempotency-Key` check, and no lookup on `event.id` (`evt_123`), so the same event delivered twice credits the customer twice. This is a financial-integrity bug, not a theoretical one: the exact redelivery path described in the context triggers it with certainty.

The fix must make the credit conditional on the event id being new, atomically. Concretely, insert the event id into a `processed_events` table keyed by id inside the same transaction and only apply the credit when the insert wins, e.g.:

```sql
BEGIN;
INSERT INTO processed_events (id) VALUES ($1) ON CONFLICT DO NOTHING;
-- credit the balance only if the above inserted (rowCount === 1)
INSERT INTO processed_events ... RETURNING (inserted);
UPDATE customers SET balance = balance + $2 WHERE id = $3;
COMMIT;
```

Verification: post the identical payload (same `event.id`) to `/webhooks/payments` twice via `curl` and assert the balance increased by exactly one `amount` — a regression test asserting this should be required.
