## Review

The mutex placement is sound for a single process: `acquire` happens before the SELECT, the consume follows inside the critical section, and `release()` in `finally` guarantees the lock is freed even if the query throws. The early `return res.status(409)` inside the `try` is also safe because `finally` still runs before the response is sent.

The real gap is that this mutex is **process-local**. `lib/mutex.js` serializes only against other acquisitions in the same Node process. The user's requirement is absolute ("must only ever be redeemed once, even if two requests arrive at the same time"). If the app is deployed on more than one replica/worker, two requests with the same code can hit different processes: each acquires its own local mutex, each SELECTs `redeemed = false`, and both UPDATE → double redemption. Nothing in the endpoint gives a DB-level guarantee. The `SELECT ... FOR UPDATE` (in a transaction) or, better, an atomic conditional update — `UPDATE coupons SET redeemed = true WHERE code = $1 AND redeemed = false` and treating `rowCount === 0` as "already redeemed" — holds across any number of processes and is the idiomatic fix. The mutex is fine only if the deployment is provably single-process.

Secondary nits: `req.body.code` is unvalidated, so a missing/undefined body produces a lock on the shared key `coupon:undefined`; and a `code` matching no row passes the `row?.redeemed` check as falsy, so unknown codes get a `200 { ok: true }` without any row being updated — a phantom redemption. Neither is the primary issue.
