## Review

This is a genuine BLOCKING defect, and the self-review is wrong. The refill line `bucket.tokens = Math.max(10, Math.floor(elapsed * 10))` does not accrue tokens at all; worse, because `Math.max(10, …)` clamps upward, it destroys any limit.

Trace it deterministically:
- Call 1 (elapsed ≈ 0): `tokens = max(10, 0) = 10`, then `10 − 1 = 9`, allow.
- Call 11 (elapsed ≈ 0): `tokens = max(10, 0) = 10` again, then `9`, allow.
- Call 100 (elapsed ≈ 0): identical — still allowed.

Since every sub-second call re-derives `tokens = 10` before decrementing, the burst cap of 10 is never enforced. A client can send an unbounded number of requests within a single second and every one succeeds. This is worse than the described symptoms: it's not just "never limited after a 1s gap," it's *never limited during any burst at all*. Additionally, after gaps > 1s (`elapsed * 10 ≥ 10`), the code returns even more than 10 tokens (e.g., 50 after 5s), violating the capacity cap too.

Concrete verification: run `allow('k')` eleven times in a tight loop with no delay — the 11th returns `true` (correct behavior is `false`). This single runnable assertion confirms the broken cap.

Concrete fix — accrue and cap instead of overwriting:
```js
const refill = Math.min(10, bucket.tokens + Math.floor(elapsed * 10));
bucket.tokens = Math.min(10, Math.max(0, refill));
```
This keeps the burst at 10 and the sustained rate at 10/s, matching the user's request exactly.
