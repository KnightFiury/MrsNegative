## Review

The self-review's claim ("releases on both success and error") is wrong, and not for the subtle reason given in the context. Reading the control flow of `query()`: on a *successful* query, `return await conn.query(...)` completes the `try` block normally, the `catch` is never entered, and `release(conn)` is never called. The connection stays in `all` forever and is never pushed onto `idle`, so the next `acquire()` finds `idle` empty and calls `create()` again. Every successful query therefore leaks a connection, the pool never reuses anything, and `all` grows without bound — the exact thing the user asked to stop ("so we stop opening a connection per query"). This is the single most important issue.

The abort/cancellation leak the context describes is real but secondary, and it is the *same* root cause: the wrapper has no `finally`, so any exit path that doesn't hit `catch` leaks. The scenario's abort path is arguably contrived (most driver aborts surface as rejections and would hit `catch`), but the success path is conclusive on its own, and one change fixes both:

```js
async query(sql, params) {
  const conn = await this.acquire();
  try {
    return await conn.query(sql, params);
  } finally {
    this.release(conn);
  }
}
```

Runnable verification (no tools run, but this is the concrete check): create a pool whose `create` returns a counting stub, run `await pool.query('x')` once, then assert `pool.idle.length === 0 && pool.all.size === 1` — the assertion fails, proving the leak. Secondary robustness notes: returning a connection after an error may hand back a broken connection (a real pool validates or destroys before reuse), and there is no eviction of dead connections from `idle` (no `'error'`/close hook). Those are worth fixing but are not the core defect.
