## Review

The code implements optimistic concurrency halfway and that half is the dangerous one. The `version` column is incremented on every write and the response returns the new version to the client — the protocol's signaling is there — but the `UPDATE` never checks the version the editor actually read (`... WHERE id = $1` only). A concrete interleaving proves the data loss the user explicitly asked to prevent: editor A reads `version = 7`, editor B reads `version = 7`, A merges onto base 7 and writes → `version = 8`, B merges onto the *same* base 7 and writes → `version = 9`. B's write silently clobbers A's edit; the version counter goes up as if everything were fine, so there is no error and no visible sign the first change was destroyed.

This is a direct violation of the request ("must not silently lose one person's changes"), so it is the primary finding and it is confirmed from the diff itself, not speculation. Two verified affects follow from the same root cause: (1) even after the guard is added, the `res.json({ version: doc.version + 1 })` computes the response from the *stale read* rather than the actual row state, so an unconditional write could lie about the resulting version; (2) there is no conflict response path at all.

Fix (concrete): pass the client's version into the write and make the version check part of the UPDATE's predicate:
```js
const result = await db.query(
  'UPDATE docs SET body = $2, version = version + 1 WHERE id = $1 AND version = $3',
  [req.params.id, merged, req.body.version],
);
if (result.rowCount === 0) return res.status(409).json({ error: 'version conflict' });
res.json({ version: 1 + Number(req.body.version) });
```
On `rowCount === 0` the loser gets a 409 and can re-read, re-merge, retry — the lost-update scenario is closed instead of confirmed. (The client must now send the version it read; it already receives it from every response, so no protocol change is needed.)
