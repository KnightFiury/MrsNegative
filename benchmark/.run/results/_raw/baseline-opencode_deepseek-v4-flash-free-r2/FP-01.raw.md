## Review

The dynamic SQL is correctly guarded and is not injection-prone in practice: `sort` can only ever be one of the three allowlisted identifiers (`SORTABLE.has(...)`), `dir` is coerced to one of two literals (`'DESC'`/`'ASC'`), and `term` is a bound parameter (`$1`). No user-controlled value reaches the SQL string except through the allowlist or the parameter array, so the "looks injection-prone at a glance" concern does not materialize.

The only real issue is a minor behavioral nitpick, not a security one: `term` is interpolated into an `ILIKE` pattern without escaping PostgreSQL LIKE metacharacters. A query like `q=100%` treats `%` as a wildcard (matching any rows containing "100" followed by anything), and `q=_` matches any single character. Parameter binding does not escape `%`/`_`. Users searching for literal percent/underscore characters will get over-broad results. The fix is to escape `\`, `%`, and `_` in `term` (e.g. `term.replace(/[\\%_]/g, '\\$&')`) before it enters the pattern.
