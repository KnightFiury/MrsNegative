## Review

This is a lost-update (TOCTOU) race that directly violates the stated requirement ("we must not silently lose one person's changes"). The handler is a classic read-modify-write with no concurrency guard:

1. Both editors run `SELECT` and see `version = 7`.
2. Both merge `req.body.changes` onto the same stale `doc.body` base.
3. Both `UPDATE` without `AND version = $3`, so each overwrites the other's merge.

The `version` column exists, is incremented on every write, and is returned to the client — yet the UPDATE never checks it, so the mechanism meant to prevent this is dead code. The failure is silent: version increments from 7 to 9 and no error surfaces, so the second editor's write appears successful while the first editor's changes are gone.

The fix is optimistic concurrency: add `AND version = $3`, take the base version from the client (e.g. `req.body.baseVersion` or `req.headers['if-match']`), and return `409 Conflict` when `rowCount === 0` so the client can re-read and re-merge. (A `SELECT ... FOR UPDATE` lock is an alternative but optimistic concurrency fits the existing version scheme better.)

Verification: a test that fires two concurrent PUTs seeded at the same base version and asserts exactly one returns `409` (or, with retry/merge, that both edits survive). This is the single most important issue in the diff and the only finding worth raising.
