## Review

The change correctly serializes the check and the consume *within a single process*: the `finally { release() }` guarantees the lock is always freed, the early `409` return happens while still holding the lock, and one request cannot interleave its read with another's write in the same Node process.

The real problem is the *scope* of that serialization. `lib/mutex.js` is described as a promise-based mutex that serializes on a key — an in-process lock with no distributed semantics. Node production deployments are rarely a single process (cluster/PW2 forking, replicated containers, serverless). On those topologies the guarantee silently breaks: a request on instance A and a request on instance B each acquire their *local* lock for `coupon:<code>`; both `SELECT` see `redeemed = false`; both run the `UPDATE`; both return `{ ok: true }`. The coupon is redeemed (reward issued) twice, which is exactly the violation the user asked to prevent. The mutex is a workaround for the wrong layer — the check-and-consume is its own naturally atomic DB operation, and the fix should live at the DB or lock layer, not in process memory.

Concrete fixes, either of which fully satisfies the requirement regardless of topology:
- Transaction + row lock: `BEGIN; SELECT redeemed FROM coupons WHERE code=$1 FOR UPDATE; ...; UPDATE ...; COMMIT;`
- Better, a single atomic statement: `UPDATE coupons SET redeemed=true WHERE code=$1 AND redeemed=false`, then respond `409` when `rowCount === 0` (optionally prevent re-insert once-redeemed codes with a unique constraint on redeemed codes).
- If locking is truly preferred, the mutex must be distributed (Redis/`SET NX`, etc.) so it is shared across instances.

A runnable verification: point two separate app instances at the same database, fire two concurrent `/api/redeem` requests with the same code, and assert exactly one response is `200` and the other `409` (currently both are `200`).

Two secondary notes: if `db.query` is node-postgres, the result is `{ rows: [...] }` and `row` above is not the row (the shaped access `row?.redeemed` would be `undefined` — not determinable from context); and a non-existent code falls through to a 0-row `UPDATE` and still returns `ok: true`.
