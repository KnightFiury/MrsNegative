## Review

The handler is **not idempotent**, which directly violates the user's explicit requirement. Per the surrounding context, Stripe delivers at-least-once: if the 200 response times out, Stripe redelivers the same event. This handler blindly runs the `UPDATE customers SET balance = balance + $2` on every arrival, with no dedup — there is no `processed_events` table, no `Idempotency-Key` check, and no guard keyed on the event id. Trace: `evt_123` arrives → balance credited → 200 times out → Stripe redelivers `evt_123` → balance credited again. The customer is credited twice for one `pi_1`, a money-correctness bug. The code also applies the credit *before* sending the 200, which is fine for at-least-once as long as dedup exists, but without it the retry path is a guaranteed double-credit.

Concrete fix: record processed event ids in a `processed_events` table (with a UNIQUE constraint on `event_id`) inside the same transaction as the credit, and only apply the balance update when the insert actually succeeded:

```sql
CREATE TABLE processed_events (
  event_id text PRIMARY KEY,
  processed_at timestamptz NOT NULL DEFAULT now()
);
```

```js
const client = await db.connect();
try {

  const inserted = await client.query(
    'INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT (event_id) DO NOTHING RETURNING id',
    [event.id],
  );
  if (inserted.rowCount === 0) {
    await client.query('ROLLBACK');
    return res.sendStatus(200); // already processed; ack without re-crediting
  }
  await client.query(
    'UPDATE customers SET balance = balance + $2 WHERE id = $1',
    [event.data.object.customer, event.data.object.amount],
  );
  await client.query('COMMIT');
  res.sendStatus(200);
} catch (e) {
  await client.query('ROLLBACK');
  throw e;
}
```

Verification: POST the same event payload (same `id`) to `/webhooks/payments` twice and assert the balance increases by `amount` exactly once; repeat with a simulated timeout-and-redelivery. Also add a regression test that delivers the event twice and asserts a single credit.

Minor (non-blocking): Stripe webhook signature verification is missing, and `db.query` errors are unhandled (an exception leaves the request hanging rather than returning a retryable 5xx — though the credit-then-200 ordering does make retries safe once dedup exists).
