## Review

The retry loop is properly bounded: `MAX_ATTEMPTS = 3` caps it, `attempt` increments on every failure path, and the backoff (100ms, 200ms) only runs between attempts, never after the last one. The code does exactly what the request asked — a few retries for a transient blip, then a clear throw. No retry storm exists here; flagging "unbounded retry" would be a false positive. The only thing worth a passing glance is that the original `err` is dropped in favor of a fresh message — losing the underlying cause makes debugging slightly harder — but that's a pre-existing style choice, not a defect, and not worth a finding.
