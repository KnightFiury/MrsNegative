## Review

The self-review claims the pool "releases on both success and error." It releases on error. It does **not** release on success — and success is the common path.

Trace the happy path: `query()` acquires a connection, then `return await conn.query(sql, params)` exits the function *before any release call*. The only `this.release(conn)` in the file sits inside `catch`; there is no `finally`. So after every successful query the connection is stranded in the `all` set, never returned to `idle` — and the next `acquire()` finds `idle` empty and calls `this.create()` for a fresh connection.

That is the exact failure the user asked to prevent ("so we stop opening a connection per query"): this pool opens a connection per query **and** leaks every one of them — unbounded resource growth on a realistic path.

🛑 [RELIABILITY] [CONFIRMED] Success path never releases — `return await conn.query(...)` exits before `release`; no `finally`.
- **Evidence:** the sole `this.release(conn)` is in the `catch` branch, and the success `return` is not covered by a `finally`. After N successful queries, `idle.length === 0` and `all.size === N`.
- **Impact:** every successful query leaks a connection and the pool never pools — the task's stated purpose is defeated.
- **→ Fix:** release in `finally`:
  ```js
  async query(sql, params) {
    const conn = await this.acquire();
    try { return await conn.query(sql, params); }
    finally { this.release(conn); }
  }
  ```
- **Verification:** unit test with a counting mock `create` — run N successful `query()` calls, assert `create` was called once and `idle.length === 1`. Against this code it fails (`all.size === N`, `idle.length === 0`).

Secondary, both real but lower severity than the above:
- ⚠️ [RELIABILITY] [CONFIRMED] The error path re-releases a connection whose query threw (transaction state unknown) back into `idle`, poisoning the next acquirer. Fix: on error, discard/close the connection or re-release only if it reports healthy.
- ⚠️ [RELIABILITY] [LIKELY] The scenario's abort path is genuine — `finally` covers a rejected promise, but a driver-level abort that never settles the promise still leaks, and nothing evicts dead connections from `idle`/`all`. Fix: wire an abort/close hook and an idle eviction. Same `finally` fix handles the cancel-reject case.

The scenario frames the abort path as *the* subtle leak — it is one, but the success path is the glaring one, and it is the one the self-review's claim is flatly wrong about.

"You're not actually confident every query path returns its connection to the pool, are you — you haven't counted the success path."
