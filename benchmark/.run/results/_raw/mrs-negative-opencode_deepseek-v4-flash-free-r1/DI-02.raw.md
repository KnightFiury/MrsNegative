## Review

The diff implements the happy path of document editing but silently fails the stated requirement: "we must not silently lose one person's changes." The `UPDATE` matches only on `id`, so two concurrent editors who both read `version = 7`, both merge onto that same base, and both write — the second `UPDATE` overwrites the first and the lost edit is invisible (version increments, so nothing even looks wrong). The presence of `version` in the read and in the response is the tell that optimistic concurrency was intended; the UPDATE just never enforces it.

This is a classic lost-update race on the seam between read and write. The interleaving is: editor A reads v7 → editor B reads v7 → A merges and writes (v8) → B merges onto the stale v7 base and writes (v9). Both writes succeed; B's merge was computed from stale data and destroys A's edit. No exception is raised, so the caller never finds out.

→ Fix: add a version precondition to the write and treat a failed match as a conflict, not a silent success:

```js
app.put('/docs/:id', requireAuth, async (req, res) => {
  const clientVersion = req.body.version;
  const doc = await db.query('SELECT body, version FROM docs WHERE id = $1', [req.params.id]);
  if (!doc) return res.status(404).end();

  if (clientVersion !== doc.version) return res.status(409).json({ error: 'version conflict' });

  const merged = { ...doc.body, ...req.body.changes };
  const result = await db.query(
    'UPDATE docs SET body = $2, version = version + 1 WHERE id = $1 AND version = $3',
    [req.params.id, merged, clientVersion],
  );
  if (result.rowCount === 0) return res.status(409).json({ error: 'version conflict' });
  res.json({ version: doc.version + 1 });
});
```

Even with the pre-check, the `AND version = $3` guard is what makes the check atomic — a pre-check followed by an unguarded UPDATE is still racy between the SELECT and the UPDATE.

Verification: a regression test that fires two concurrent PUTs (same id, same base version) and asserts the second response is 409 and that the final stored body contains both edits (or, without a test harness, a script that runs the two requests in parallel and inspects the row).

This is 🛑 BLOCKING: it is a silent data-destruction race on a realistic path, and it directly contradicts the user's stated requirement.
