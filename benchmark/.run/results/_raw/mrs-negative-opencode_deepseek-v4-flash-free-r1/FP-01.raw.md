## Review

At a glance this smells like SQL injection, but it isn't — and it's worth saying exactly why rather than hand-waving. Every fragment that reaches the SQL string is either a compile-time constant or a bound parameter:

- `sort` is gated through `SORTABLE.has(...)` before interpolation, so the only strings that can enter the `ORDER BY` slot are `name`, `email`, or `created_at` — attacker-controlled values fall back to the literal `'name'`.
- `dir` is coerced by the ternary into one of two literals, `'DESC'` or `'ASC'`; any other input yields `'ASC'`.
- `term` goes into the query only as the `$1` bound parameter.

There is no code path where a raw user string reaches the query string. The injection concern is a verified non-issue, and the fix here (a naive `ORDER BY ${req.query.sort}` or `LIKE '%' + req.query.q + '%'`) is precisely what this code is already doing differently.

The only thing close to a finding is that `%` and `_` inside `term` aren't escaped in the ILIKE pattern, so a search for `%` matches every row. But this is an admin-authenticated search endpoint where the operator controls their own search term — it's expected wildcard behavior, not a risk to anyone. Raising it would be noise.

The change does exactly what the request asked for: a filtered, sortable admin list endpoint. Nothing to fix, nothing to flag.
