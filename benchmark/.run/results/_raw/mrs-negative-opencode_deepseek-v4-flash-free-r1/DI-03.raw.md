## Review

The code does exactly one thing — credit the balance — and it's the one thing the request told you to guarantee against doing twice. The handler blindly increments on every arrival with no dedup of any kind, against a documented at-least-once delivery contract. That's the primary finding, and it's the request's stated intent violated outright.

🛑 [RELIABILITY] [CONFIRMED] No idempotency — the same event credits the balance twice.
   Evidence: the repo's own docs state Stripe delivers at-least-once; the handler credits first and acks with 200, so a lost 200 (the documented redelivery trigger) makes Stripe resend `evt_123`, and the same `UPDATE ... balance = balance + $2` runs again. Two concurrent redeliveries race identically — nothing serializes them.
   Impact: a customer is credited twice for one payment — exactly what the user request forbade.
   → Fix: dedupe on the Stripe event id. Add `processed_events(event_id TEXT PRIMARY KEY)` and credit only when the insert wins: `INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING`, then `UPDATE` only if a row was actually inserted. The unique constraint makes concurrent redeliveries safe too, since only one INSERT can win.
   Verification: POST the same webhook payload twice (and twice concurrently); assert the balance moved by exactly one credit.

⚠️ [SECURITY] [UNVERIFIED] The handler never verifies the `Stripe-Signature` header.
   Evidence: the diff doesn't read the header; I couldn't check whether middleware elsewhere does it — assumed, not verified.
   Impact: anyone who can reach the endpoint can POST a forged `payment_intent.succeeded` and credit their own balance.
   → Fix: verify the signature with Stripe's library before touching the DB.
   Verification: POST a payload with an invalid/absent signature and assert it's rejected with 400.

💭 [CORRECTNESS] [UNVERIFIED] `data.object.amount` is in the smallest currency unit (cents for USD) and is not the amount actually captured.
   Evidence: Stripe's field semantics — assumed, not verified against this repo's `balance` unit convention.
   → Fix: use `amount_received` and confirm `balance` stores the same unit.
   Verification: send a known $10.00 payment and assert the credited delta.
