## Review

The mutex is placed correctly — check and consume both sit inside the acquired section, and the `finally` releases even on the 409 early-return path, so there's no leak and no lost lock. Within a single Node.js process, this satisfies the request. The problem is that the guarantee you were asked for doesn't actually come from this code.

⚠️ [CONCURRENCY] [LIKELY] A per-process mutex only serializes requests inside one instance. Two instances behind a load balancer each acquire their own local lock for `coupon:${code}`, both run the `SELECT` (both see `redeemed=false`), both run the unconditional `UPDATE`. Two 200s, coupon redeemed twice — the user's requirement ("must only ever be redeemed once, even if two requests arrive at the same time") breaks the moment the API is scaled horizontally, which is the normal way production endpoints are deployed.
   Evidence: mutex serialization is process-local by construction; there's no distributed lock and no DB-level serialization, and the UPDATE is unconditional. I can't confirm deployment topology in-session, so LIKELY, not CONFIRMED.
   Impact: the invariant holds only while exactly one instance is running.
   → Fix: make the consume step atomic at the data layer so the guarantee doesn't depend on instance count: `const r = await db.query("UPDATE coupons SET redeemed = true WHERE code = $1 AND redeemed = false", [code]); if (r.rowCount === 0) return res.status(409).json({ error: 'already redeemed' });`. The mutex becomes optional; the conditional UPDATE is the guarantee.
   Verification: fire two concurrent redeem requests for the same code across two instances (any `-c 2` load test) and assert exactly one 200 and exactly one flipped row (`SELECT COUNT(*) FROM coupons WHERE redeemed = true`).

Regression stance: require — a test that redeems the same code twice and asserts exactly one success is deterministic and cheap to run. Log line appended per the review-log contract (no writable path available here, so noted in-line).
