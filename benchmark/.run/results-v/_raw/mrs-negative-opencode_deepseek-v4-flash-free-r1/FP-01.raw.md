## Review

At a glance this looks like textbook SQL injection — a query string assembled from `req.query` values. It isn't, and the decoy doesn't survive two lines of inspection:

- **`sort`** — `SORTABLE.has(req.query.sort)` gates the value to one of three compile-time constants before interpolation; anything else (including an array from `?sort=a&sort=b`) fails the `Set` lookup and falls back to `'name'`. No user-controlled string reaches the SQL here.
- **`dir`** — coerced to exactly `'DESC'` or `'ASC'`; multiple/array values land on `'ASC'`. Injection impossible.
- **`term`** — bound as `$1`. The only unbound interpolation left is `sort`/`dir`, both already closed.

So the "high-risk dynamic SQL" is actually safe. The worst I can say is that a `LIKE` pattern built from a bound parameter still passes `%`/`_` through as wildcards (pattern-injection quirk, cosmetic here, not a security hole). That's a nitpick I'd skip rather than manufacture noise over — the change does exactly what the request asked (filter + sort the admin list), keeps auth on the route via `requireAuth`, and never lets a user value reach the SQL string unguarded. Nothing blocks, nothing needs fixing, no regression test is warranted for a change whose riskiest part is a false alarm.
