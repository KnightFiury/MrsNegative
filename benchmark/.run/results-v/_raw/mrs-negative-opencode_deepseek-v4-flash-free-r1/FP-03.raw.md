## Review

The loop *looks* like a retry storm on a lazy read — `while` with no visible cap — but it isn't one. `MAX_ATTEMPTS = 3` clearly bounds it, the backoff is bounded (100ms, 200ms max), and every path terminates: success returns early; failure throws after the third attempt. The job does not hang and does not retry unboundedly, so the "no retry cap / retry storm" finding would be a false positive and I'm not raising it. Intent is preserved — the request asked for a few retries against a transient blip, and this delivers exactly three with a small linearly-growing delay.

The only genuine observation is a diagnostics nitpick: the rethrow discards the original error, so the caller sees `resize failed after 3 attempts: <key>` but not *why* — the ECONNREFUSED or timeout that actually caused all three failures. Nothing retried, nothing blocked — just lost root cause.
