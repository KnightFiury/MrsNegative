## Review

The mechanism is sound within one process, and only within one process. A promise-based mutex in `lib/mutex.js` is inherently in-memory and process-local — it serializes on the key only for requests that land on the *same* Node instance. The moment two requests for the same code arrive on two instances sharing the same `coupons` table (horizontal scaling, worker processes, a restart mid-request), each passes its local lock, both run `SELECT` (both see `redeemed=false`), both run the `UPDATE`, and both return `{ ok: true }`. The user's requirement — "must only ever be redeemed once, even if two requests arrive at the same time" — is stated unconditionally, and this code only satisfies it for a single-instance topology.

⚠️ [CONCURRENCY] [LIKELY] The per-code mutex only serializes within one process; the once-only guarantee silently breaks across instances.
- Evidence: multi-instance interleaving — P1 and P2 each `await mutex.acquire('coupon:X')` on their own process-local mutex, both SELECT `redeemed=false`, both UPDATE, both respond `ok:true`. `mutex.js` is a promise mutex (in-memory, per-process), and no cross-process coordinator exists in the diff; verified it serializes only on the key within the process — deployment topology not visible from the repo, so LIKELY, not CONFIRMED.
- Impact: the same coupon is consumed twice under concurrent load, the exact failure the user said must never happen.
- → Fix: make the database the authority — `UPDATE coupons SET redeemed = true WHERE code = $1 AND redeemed = false` and return 409 when `rowCount === 0`; or wrap check+consume in a transaction with `SELECT ... FOR UPDATE`. Both hold under any process count.
- Verification: run two separate Node processes executing the handler against the same DB, fire both for the same code concurrently, assert exactly one 200 and one 409 (or, against the fix, assert the rowCount gate trips); a regression test can assert the redeemed row count is exactly 1 after N concurrent attempts.

💭 [RELIABILITY] [CONFIRMED] `row?.redeemed` treats a missing coupon (`row === null`) as not-yet-redeemed, so an unknown code falls through to an UPDATE that affects 0 rows and returns `ok:true`.
- → Fix: return 404/400 when `!row` before the redeemed check.

Regression stance: require a test pinning the once-only guarantee across two processes; a single-process test can't catch the gap the fix addresses.
