## Review

The mutex discipline in this diff is correct *within a single process*: `acquire` runs before both the SELECT and the UPDATE, `release` is in a `finally`, and the early `return res.status(409).json(...)` still triggers the release. There is no interleaving window in one process, and reentrancy isn't an issue since each request locks its own key and `release` is idempotent.

The real gap is architectural: `lib/mutex.js` is an in-memory promise queue, so the guarantee only holds per V8 isolate. If this service ever runs more than one instance (PM2 cluster, multiple replicas behind a load balancer, serverless), the "must only ever be redeemed once" invariant breaks:

- P1 acquires its process's mutex for `coupon:X`; P2 acquires its own process's mutex for the same key (both succeed).
- P1 runs `SELECT ... WHERE code='X'` → sees `redeemed = false`.
- P2 runs the same SELECT → also sees `false`.
- P1 UPDATE, P2 UPDATE, both return `{ ok: true }`.

Nothing in the DB enforces uniqueness, so the invariant rests entirely on app-level coordination. The canonical fix is to make the consume atomic in the database — e.g. `UPDATE coupons SET redeemed = true WHERE code = $1 AND redeemed = false` and treat `rowCount === 1` as success, `rowCount === 0` as 409 — which holds regardless of process count, crash timing, or a stale lock. The mutex can stay as a throttling/UX nicety; it just should not be the source of truth.

Minor: `code` is interpolated into the lock key without normalization. Undefined/null payloads all lock on `"coupon:undefined"`, which is harmless to correctness (just unnecessary serialization) but worth a `String(code)` guard.

Verification: run two instances of the app and fire concurrent POSTs with the same code at both — today both return 200. After switching to the atomic conditional UPDATE, re-run and observe exactly one 200 and one 409.
