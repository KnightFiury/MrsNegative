# Benchmark results — format and conventions

`results/` is for **run output**, not committed cases. Store one result
JSON per case (or per run) here, then score with `node
scripts/score.mjs results/`.

## How a run is produced

The benchmark cases live in `cases/`. For each case, the model (via the
adapter being validated) reviews the code change in the case body **without
seeing the "Expected outcome" section**. The model's output is then
translated into the result format below.

Translation of prose output is done by a judge — a human or an LLM-judge
using `rubric.md` as the adjudication standard. The judge fills the
`output` object. The scripts themselves are deterministic: they never
interpret prose.

## Result file format

One JSON file per case, named `<CASE_ID>.json` (any name with a
`caseId` field also works):

```json
{
  "caseId": "SEC-01",
  "model": "model name (optional)",
  "adapter": "adapter name (optional)",
  "output": {
    "hasFinding": true,
    "severity": "BLOCKING",
    "evidence": "CONFIRMED",
    "primaryFound": true,
    "evidenceBacked": true,
    "verificationConcrete": true,
    "fixConcrete": true,
    "intentPreserved": true,
    "regressionStance": "require",
    "regressionAppropriate": true,
    "inventedSeverity": null,
    "unverifiedEscalated": false,
    "notes": ""
  }
}
```

### Field meanings

| Field | Values | Meaning (judge fills) |
|---|---|---|
| `hasFinding` | bool | Did the output report any finding at all? |
| `severity` | `BLOCKING` / `WORTH-FIXING` / `NITPICK` / `null` | The tier of the output's primary (or only) finding; `null` when silent. |
| `evidence` | `CONFIRMED` / `LIKELY` / `UNVERIFIED` / `N/A` / `null` | The evidence level the output claimed. |
| `primaryFound` | bool | Did the output surface the expected primary finding (semantic match)? |
| `evidenceBacked` | bool | Did the output show concrete proof — payload, input-to-sink trace, interleaving, docs read — rather than a bare label? |
| `verificationConcrete` | bool | Did the output name a concrete, runnable verification (payload/command/test)? |
| `fixConcrete` | bool | Did the output give a concrete, correct fix? |
| `intentPreserved` | bool | Did the output correctly read the user request and catch (or avoid inventing) semantic violations? |
| `regressionStance` | `require` / `confirm` / `decline` / `skip` / `null` | The output's stance on a regression test. |
| `regressionAppropriate` | bool | Was that stance correct for this case (require on BLOCKING, confirm on a verified fix, decline/skip on NITPICK or safe)? |
| `inventedSeverity` | `BLOCKING` / `WORTH-FIXING` / `NITPICK` / `null` | Worst tier among findings the output invented (not in the expected answer). `null` = none. |
| `unverifiedEscalated` | bool | Did the output claim `UNVERIFIED` evidence but escalate to `BLOCKING` anyway? |
| `notes` | string | Free text for the judge; not scored. |

## Scoring

Run:

```bash
node scripts/validate.mjs        # regenerates expected/answers.json
node scripts/score.mjs results/  # scores everything under results/
```

`score.mjs` writes `results/latest-report.md` and prints it. Per-case
scores (8 dimensions × 5 + FP multiplier) and the finding-level aggregates
(precision/recall/BLOCKING precision/BLOCKING recall, rates) are all in the
report.

## Rules of engagement

- Never edit `results/` to make a score better. If a case is wrong, fix the
  case and bump the version per `version.md`.
- Never change `expected/answers.json` by hand — it is regenerated by
  `validate.mjs`.
- A run is only comparable to another run of the same benchmark version.
